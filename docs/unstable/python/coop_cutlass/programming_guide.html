Programming Guide#

This guide starts with a complete program and explains its parts. It then runs that program on more than one block, shows how primitives reach the values of CuTe tensors, lists the operations, and ends with how to check and tune a kernel. Programming concepts introduces the ideas the primitives share, and the API reference documents every primitive.

A first program#

This program computes the running sum of 512 integers with one block of 128 threads. Each thread loads four items, the block computes the running sum across all of them, and each thread stores its four results:

# Copyright (c) 2026, NVIDIA CORPORATION & AFFILIATES. ALL RIGHTS RESERVED.
#
# SPDX-License-Identifier: Apache-2.0 WITH LLVM-exception

"""Compute the running sum of 512 integers with one block of 128 threads."""

import cutlass
import numpy as np
from cutlass import cute
from cutlass.cute.runtime import make_ptr

import cuda.coop.cutlass as coop
from cuda.bindings import driver


# docs: start cutlass-prefix-sum
@cute.kernel
def prefix_sum(
    source: cute.Pointer,
    destination: cute.Pointer,
    items_per_thread: cutlass.Constexpr,
):
    block = coop.this_block()
    values = coop.load(block, source, items_per_thread=items_per_thread)
    sums = coop.inclusive_sum(block, values)
    coop.store(block, destination, sums)


@cute.jit
def launch(
    source: cute.Pointer,
    destination: cute.Pointer,
    items_per_thread: cutlass.Constexpr,
):
    kernel = prefix_sum(source, destination, items_per_thread)
    kernel.launch(grid=1, block=128)
    # docs: end cutlass-prefix-sum


def _check(result):
    """Raise on Driver errors and unwrap a single returned handle or value."""

    if int(result[0]):
        raise RuntimeError(f"CUDA Driver call failed: {result[0]}")
    return result[1] if len(result) == 2 else result[1:]


def run_example(items_per_thread=4):
    """Launch the kernel and compare its output with numpy.cumsum."""

    source = np.arange(128 * items_per_thread, dtype=np.int32)
    result = np.zeros_like(source)
    cutlass.cuda.initialize_cuda_context()
    src = _check(driver.cuMemAlloc(source.nbytes))
    try:
        dst = _check(driver.cuMemAlloc(result.nbytes))
        try:
            _check(driver.cuMemcpyHtoD(src, source.ctypes.data, source.nbytes))
            # The source pointer's type tells load that the items are Int32.
            launch(
                make_ptr(cutlass.Int32, int(src), cute.AddressSpace.gmem),
                make_ptr(cutlass.Int32, int(dst), cute.AddressSpace.gmem),
                items_per_thread,
            )
            _check(driver.cuCtxSynchronize())
            _check(driver.cuMemcpyDtoH(result.ctypes.data, dst, result.nbytes))
        finally:
            _check(driver.cuMemFree(dst))
    finally:
        _check(driver.cuMemFree(src))
    np.testing.assert_array_equal(result, np.cumsum(source, dtype=np.int32))
    return result


if __name__ == "__main__":
    run_example()

Run it from the repository root:

python python/cuda_coop_cutlass/examples/prefix_sum.py

The kernel has four lines. Each one shows something that Programming concepts explains:

  • coop.this_block() is a thread group, the 128 threads that make each call together.

  • coop.load returns each thread’s four items as a ThreadData, and coop.store writes one to memory.

  • coop.inclusive_sum(block, values) is a single-phase call. It takes the block size from the launch, and the element type and item count from values.

  • coop.inclusive_sum also needs scratch space in shared memory, and the compiler provides it. A kernel that wants to size or share that space passes a TempStorage.

On the host side:

  • make_ptr(cutlass.Int32, ...) gives each pointer its element type. That is how load knows the items are Int32. store takes the type from the ThreadData it writes, so its pointer must have the same type. A pointer to unsigned integers reaches the kernel as the signed type, so for Uint32 data pass dtype=cutlass.Uint32 to load() and store().

  • items_per_thread is declared cutlass.Constexpr in the kernel and in the launcher, so its value is known when the kernel is compiled.

  • kernel.launch(grid=1, block=128) sets the block size.

The first call to launch compiles the kernel. Each later call runs the Python code of the launcher and the kernel again, even when CuTe then reuses the compiled kernel. Checking and tuning a kernel shows how to compile once and launch many times.

More than one block#

This kernel runs the scan of the first program on a grid of blocks, where each block computes the running sum of its own tile:

Download the full example and test

@cute.kernel
def prefix_sum_per_block(
    source: cute.Pointer,
    destination: cute.Pointer,
    items_per_thread: cutlass.Constexpr,
):
    block = coop.this_block()
    # A block of 128 threads owns 128 * items_per_thread elements.
    offset = cute.arch.block_idx()[0] * 128 * items_per_thread
    values = coop.load(
        block, source, items_per_thread=items_per_thread, offset=offset
    )
    sums = coop.inclusive_sum(block, values)
    coop.store(block, destination, sums, offset=offset)

Each block is a group of its own. Its ranks start at 0, and its scan starts again with its first item. load and store never add the block index, so blocks that pass the same offset work on the same tile. This kernel passes an offset computed from cute.arch.block_idx(): the block’s index along x, times the 128 * items_per_thread elements of one tile.

The test launches the kernel with grid=3, block=128 and four items per thread. The three blocks work on elements 0 to 511, 512 to 1,023 and 1,024 to 1,535. Thread groups in the API reference has the rules that hold for every group.

Working with CuTe tensors#

Where a tensor keeps its values decides how a primitive reaches them:

The values are in

A primitive reaches them through

Global or shared memory, behind a CuTe pointer or tensor

load() and store()

A CuTe register tensor, made with cute.make_rmem_tensor

from_register_tensor() and to_register_tensor()

A TensorSSA, such as the result of tensor.load()

from_vector() and to_tensor_ssa()

load takes its source, and store its destination, as a CuTe pointer or as a tensor whose shape and strides are Python values and form a compact layout. cute.make_tensor(pointer, cute.make_layout(n)) is such a tensor. So are a shared tensor from CuTe’s SmemAllocator and a tensor from TempStorage.reserve. A register tensor is rejected there when the kernel is compiled. The entry for load() lists every form and says when the size of the memory is checked.

Values that are already in registers become a payload through the conversions of ThreadData. Each conversion copies.

Advanced topics covers kernels that run native CuTe code next to the primitives: staging a tile in shared memory with a native CuTe copy, typed workspaces that native code and primitives use in turn, and register loads that another object owns.

Checking and tuning a kernel#

Check a kernel’s results against a reference computed on the host before you time it. Check which thread holds each value as well as the values. Cover the cases your application uses: a partial tile, an offset other than zero, more than one warp or group of lanes, and scratch that is reused. Compare only the results that a primitive defines. Each entry in the API reference says which threads and which items those are.

Keep compilation out of the time you measure. cute.compile takes the @cute.jit function that launches the kernel, followed by that function’s arguments, and returns a callable that you keep. Call it for each launch with the arguments that are not declared cutlass.Constexpr. The debugger walkthrough compiles once and launches twice. The first compilation generates the C++ behind the kernel’s primitives, compiles it with NVRTC and links it into the kernel. Another cute.compile of the same kernel takes the compiled C++ from the package’s cache on disk, then compiles and links the kernel again. Synchronize after the launches you measure and before you read the clock, as the examples do with driver.cuCtxSynchronize().

To read the generated C++, set CUDA_COOP_CUTLASS_SOURCE_DUMP_DIR before the kernel is compiled. Configuration describes the variable. Judge inlining, barriers, shared memory and register use from the final linked cubin, which CuTe keeps when CUTE_DSL_KEEP=cubin is set. CuTe writes the cubin to the current directory, or to the one that CUTE_DSL_DUMP_DIR names. Set the two CuTe variables before the program starts. cuobjdump --dump-sass lists the cubin’s instructions, where LDS and STS are the shared-memory accesses. cuobjdump --dump-resource-usage lists its registers and static shared memory. That report can leave out a primitive’s scratch, and TempStorage shows how to measure it in the kernel. The link can still inline the code of a primitive into the kernel, so the generated source and the PTX from before the link show an earlier stage. Run Compute Sanitizer’s race check after you change how a kernel reuses scratch or where it synchronizes.

More items per thread can raise register use, and more scratch can lower the number of blocks that fit on a multiprocessor at the same time. Look at the compiled kernel’s resource use as well as its run time.
